# The Ubuntu Touch click (arm64)

Packages what `kn/` builds — PhotonCamera as one Kotlin/Native executable, no
JVM, no ART, no Android runtime — as an arm64 click for `ubuntu-touch-24.04-1.x`.

    clickable build --arch arm64                   # from a fresh clone
    kn/click/make-click.sh                         # the fast loop, on this box

## The two ways to get the binary

`kn/click/build.sh` either compiles the Kotlin/Native binary in the cross
container or packages one the host already linked, and **the build log says
which happened**.

| | When | What it costs |
| --- | --- | --- |
| **source** | no staged tree, or one older than a source file | the first run clones aurora-maven (922 MB) and downloads konan and the Compose klibs; ~40 min |
| **staged** | `kn/out/click-prebuilt` is there and newer than every source | seconds — it only assembles the click |

`PC_CLICK_BUILD=source` forces a rebuild; `PC_CLICK_BUILD=staged` packages the
staged tree even if it is stale, which is the escape hatch when the source build
breaks. Clickable passes nothing of your environment into the container, so it
is spelled `CLICKABLE_ENV_PC_CLICK_BUILD=…` on the outside — `CLICKABLE_ENV_x`
becomes `x` in there, and that is what `make-click.sh` uses.

**Kotlin/Native is not the obstacle it was once described as here.** Konan ships
no linux-aarch64 *host* compiler — the bundle is
`kotlin-native-prebuilt-linux-x86_64-*`, and that name is the host, not the
target — so a native or emulated arm64 container could never have `konanc`. But
this click builds in the **amd64 cross container**, where konan runs and
cross-compiles by design, exactly as the JVM port compiles its whole world in
the same place. What actually blocked a container build was that `auroraMaven`
and the arm64 sysroot were hardcoded to absolute paths outside the project root,
and clickable mounts the project root and nothing else.

## The two out-of-tree inputs

Both are inputs, not sources; neither is patched or forked; both are public.

| | What | Where it comes from |
| --- | --- | --- |
| `kn/deps/aurora-maven` | Aurora's CMP fork as a maven repository — the Compose and skiko klibs, and the aarch64 `libmaliit-glib` this click bundles | `git clone --depth 1 --branch aurora-0.0.4 https://hub.mos.ru/auroraos/kotlin-multiplatform/aurora-maven.git` (922 MB, git-lfs) |
| `kn/deps/sysroot-arm64` | an Ubuntu noble arm64 sysroot | assembled from ports.ubuntu.com debs (141 MB) |

`kn/scripts/fetch-deps.sh` fetches both and **skips whatever already answers**,
in the same order `kn/settings.gradle.kts` resolves them:

1. `PC_AURORA_MAVEN` / `PC_ARM_SYSROOT`, or `-PauroraMaven` / `-ParmSysroot`
2. `kn/deps/…` — the in-project clone, which is what CI and the container use
3. this developer box's `aurora-probe` checkout

The last entry is why the existing workflow here costs no extra disk: a box that
already has aurora-probe downloads nothing, and only a fresh clone pays the
922 MB. The in-project copy has to be a **real** directory — a symlink out of
the project root resolves to nothing inside the container.

`git-lfs` is not optional: without it the clone succeeds and every klib in it is
a 130-byte pointer file, which fails much later and says nothing about why.
`fetch-deps.sh` refuses to clone without it, and checks free disk first.

## What a fresh clone actually builds

The **converted app** (`kn/gen`, `kn/gen-atlas`) is generated by the j2k pipeline
and is not tracked, so a fresh clone has neither and the container build links
the milestone-2 **UI-only** binary — it says so in the log. With those trees
present (this box), the same command adds `-PwithApp` and builds the app,
including the natives and atlas's camera backend. Making the app itself
reproducible from a clone is the j2k lane's problem, not the packaging's.

An arm64 `ncnn` (`kn/out/ncnn-arm64`) is used when it is there and skipped with a
note when it is not; without it FlowNet and KernelNet report unavailable.
`kn/host/natives/build_ncnn.sh` builds one, and the click build does not run it.

## Why this is so much smaller than `linux-port/click`

The JVM port's click carries a jlinked OpenJDK, atlas's framework as jars, ART's
boot jars, a CDS archive and eleven native objects, and compiles most of that in
the container. This one has no runtime to carry: Kotlin/Native linked everything
the app is into one ELF, and the C the port needs (mgwl, the camera backend, the
app's own natives, ncnn) is *inside* that ELF as static archives. So there is no
`classpath/`, no `jvm/`, and `lib/` holds exactly one library.

    photoncam-kn               the executable (46 MB)
    resources/                 Compose's own resources, staged by the Gradle link
    assets/                    app/src/main/assets: shaders, LUTs, ncnn models
    lib/libmaliit-glib.so*     the one library Ubuntu Touch does not ship
    run.sh                     the launcher the .desktop Exec= points at
    manifest.json photoncamera.{desktop,apparmor,png}

`dependencies_host` in `clickable.yaml` is what the source build needs and
nothing more — a JDK for Gradle and konan, `git`/`git-lfs` for aurora-maven,
`curl` for the sysroot debs, the aarch64 cross gcc and clang for mgwl, the
camera backend and the app's C++, `pkg-config` for glib — plus the three the
packaging itself uses: `file` to prove every staged object is aarch64,
`binutils` for the `readelf` the closure check runs, and `python3`.

## The appid

`photoncamera.thekit`, hook (and therefore `.desktop` basename) `photoncamera`.

* `.thekit` is the OpenStore developer suffix the sibling packages from this
  checkout already use (`monogram.thekit`, `cmpprobe.thekit`, `geckopane.thekit`),
  and the suffix *must* be the OpenStore account name or the upload is rejected.
  The JVM port's `photoncamera-jvm.nekit` is a different identity and is not
  reused: keeping the names apart also means both clicks can sit on one phone
  during bring-up.
* The hook name is `photoncamera` and not `photoncamera-kn` because it is what
  the user sees in the launcher, and because the Kotlin/Native port is meant to
  become *the* port rather than a variant of one.
* `build.sh` fails the build if the manifest hook and the `.desktop` basename
  drift apart — `run.sh` leans on them matching (see `PC_APP_ID` below).

## The libraries: what ships and what the phone already has

`readelf -d` on the binary names 25 `DT_NEEDED`. Checked one by one against
`device-libs.txt` (a OnePlus 11 on 24.04.4 `ldconfig -p`), **24 of the 25 are on
the device** — Qt5Core/Qt5DBus, EGL/GLESv2, the three wayland libraries,
xkbcommon, fontconfig, dbus-1, gobject/glib, stdc++, zstd and the libc set.
`dependencies_target` in `clickable.yaml` is that same list as `-dev` packages:
nothing links against them here, but they are the contract the binary was linked
against (`kn/build.gradle.kts`'s `commonLibs`).

The one exception is **`libmaliit-glib.so.0`, and it ships.** compose-ui's klib
manifest names `ak-keyboard-maliit`, so `-lmaliit-glib` is on the link line
whether or not a keyboard is ever shown, and the loader demands it at start-up.
Ubuntu Touch carries `libmaliit-plugins.so.2` but no glib bindings, so only a
phone that has had a Qt keyboard app installed happens to have one; everywhere
else the process dies with `error while loading shared libraries` before
`main()`. That is the failure `scripts/run-phone.sh` pushes it to avoid, and
this is the packaged form of the same fix.

`build.sh` looks for it in the container's own `/usr/lib/aarch64-linux-gnu`
first, then `kn/deps/aurora-maven`, then the staged copy — but **the container
never answers**: noble's `libmaliit-glib-dev:arm64` is maliit 2.3.0, whose
soname is `libmaliit-glib.so.2`, while the binary needs `.so.0`, which is
Aurora's 0.99.1 build. Verified by running the build: it bundles
aurora-maven's. The package stays in `dependencies_target` as the link contract.
Either way it does not take the result on trust: step 3 walks the `DT_NEEDED`
closure of everything staged and fails the build, naming the library, when one
is neither in `device-libs.txt` nor in the package. That is the check
`linux-port/click/build.sh` has, and it is what keeps "it linked on the host"
from meaning "it loads on the phone".

**Deliberately not shipped:** `libcamera2ndk.so`, `libmediandk.so`,
`libbinder_ndk.so` and `libcamera_metadata.so`. Those are the *device's own*
Android libraries; `host/atlcamera/src/camera_backend_camera2ndk.c` loads them
through libhybris' `android_dlopen`, not through the host loader, because they
are bionic objects. A glibc copy would be useless. `libhybris-common.so.1` is on
the device and is already in the process (the session preloads it), which is why
the backend looks the loader up with `dlsym(RTLD_DEFAULT, …)` first.

## What the launcher sets, and why each line is there

`run.sh` is the packaged form of `scripts/run-phone.sh`'s remote half. It uses
**shell builtins only** until the final `exec`, because click confinement
forbids exec'ing anything outside the package — no `id`, no `readlink`, no
`pgrep`.

| Variable | Why |
| --- | --- |
| `LD_LIBRARY_PATH=$APP_DIR/lib` | finds the bundled maliit-glib |
| `GLIBC_TUNABLES=glibc.rtld.optional_static_tls=4096` | the hybris linker is dlopen'd after this process has its own TLS; on a Mali device there is otherwise no room and it fails with "cannot allocate memory in static TLS block" |
| `ATL_APPDIR=$APP_DIR` | `host/appdir_stub.c` answers Aurora's `appdir_get_path(PACKAGE_FILES)` with it, and CMP's resource reader appends `/resources` |
| `PHOTONCAMERA_ASSETS=$APP_DIR/assets` | the GL pipeline's shaders and the ncnn models |
| `PHOTONCAMERA_HOME=$HOME/Pictures/PhotonCamera` | the one writable root — see below |
| `ATL_UGLY_ENABLE_CAMERA`, `ATL_CAMERA_BACKEND=camera2ndk`, `ATL_SDK_INT=34` | atlas gates the camera behind an opt-in; the backend is pinned so a phone without hybris camera2 fails loudly instead of offering a backend with no RAW stream |
| `PC_APP_ID=$APP_ID` | **the one that decides whether the app takes a tap** |
| `WAYLAND_DISPLAY` / `PC_SOCKET` | absolute path to the real compositor socket |

`PC_APP_ID`: Mir hands touch, and Lomiri a foreground lifecycle, only to a
surface the shell can match to the application it started — by app id. For a
click that is the `<pkg>_<app>_<version>` triplet Lomiri exports as `APP_ID`;
`Main.kt` falls back to the literal `photoncamera`, which is the `.desktop`
basename and is right for a hand-made launcher entry. With the two out of step
the shell decides this is a background app and SIGSTOPs it.

The Wayland socket: Lomiri remaps `XDG_RUNTIME_DIR` for a confined app and the
compositor's socket is not in the remapped one. libwayland accepts an absolute
`WAYLAND_DISPLAY`, so the launcher finds `/run/user/<uid>/wayland-0` (uid read
out of `/proc/self/status`, since `id` cannot be exec'd) and passes the path.

`GRID_UNIT_PX` needs no handling: a click app inherits it from Lomiri, and the
UI density is that over 8. Started any other way it is absent and the app lays
out at density 2, which is not what the phone shows.

The final argument is `0`. It is a *run length in seconds* and 0 means "until
the window closes" — the bring-up default is 10, so an app launched without it
would vanish ten seconds in and look like a crash.

Not the launcher's business, but worth knowing when reading a screenshot: a
Lomiri-managed app loses the top 63 px to the indicator panel.

## AppArmor: two policy groups, and why not more

    "policy_groups": ["camera", "picture_files"]

* **`camera`** — the whole point. The capture path is the device's own Android
  camera2 stack reached through libhybris.
* **`picture_files`** — `FileManager.CreateFolders()` makes `DCIM/Camera` and
  `DCIM/PhotonCamera/{Raw,Tuning}` under the external-storage root, and every
  capture is written there. The launcher puts that root inside `~/Pictures`,
  which is what this group grants and where the gallery looks.

Groups this app is often assumed to need and **does not**, on this port, today:

* **`audio` / `microphone`** — there is no audio backend at all.
  `android/media/AudioRecord.kt` says so in its header: nothing wires up
  PulseAudio or ALSA, so `FlacAudioRecorder` builds a recorder that never
  initialises and every caller takes its no-microphone path. `AudioManager` is a
  no-op object. Both groups go in the moment an audio backend lands — the FLAC
  recorder is real C and is already linked in.
* **`networking`** — `Specific`, `SupportedDevice` and `SensorSpecifics` do fetch
  device tuning from raw.githubusercontent.com on Android, but this port's
  `java.net.HttpURLConnection` throws `no network client on this port` by
  construction (`src/commonMain/kotlin/java/net/JavaNet.kt`). The offline copies
  in `assets/specific/` are what is actually read.
* **`content_exchange`** — there is no share path to grant. `Context.startActivity`
  on this port logs the intent and drops it; there is no activity manager. When
  the gallery tile learns to hand a JPEG to content-hub, this is the group.

`policy_version` is `2404.1`, matching every other 24.04 click in this checkout.

## Building, reviewing, installing

    clickable build --arch arm64 --skip-review   # self-contained; slow first run
    kn/click/make-click.sh                       # host link + stage, then the above

    clickable review --arch arm64                # the click-review findings
    clickable install --ssh <device>             # hostname only: clickable
                                                 # prepends phablet@ itself

The first command needs nothing but a clone, podman/docker and network. The
second is the fast loop on a box that can already link arm64: it runs the host
Gradle build, stages the result, and `build.sh` then takes the staged path.

    PC_CLICK_BUILD=source clickable build --arch arm64    # ignore the staged tree
    PC_CLICK_BUILD=staged clickable build --arch arm64    # package it even if stale

`--container-mode` runs the build script **without a container**, on the host
itself, against whatever this machine resolves — including the out-of-tree
`aurora-probe` paths — with no image and no 922 MB clone. Two things about it,
both found by running it:

    clickable build --arch arm64 --container-mode --skip-image-setup --skip-review

* `--skip-image-setup` is not optional. Container mode installs
  `dependencies_host` on *this* machine, and without root that fails on
  `/var/lib/apt/lists/lock` before the build script runs at all.
* it stages the tree and then stops at `click: command not found`, because
  packing the `.click` is the `click` tool's job and a normal desktop has no
  `click-dev`. So container mode is useful for exercising `build.sh` and for a
  machine that has the packaging tools, not for producing a click here.

`make-click.sh` passes `--skip-review` for the same reason the JVM port's does —
the review is worth running deliberately, on its own, rather than in the way of
every rebuild. Anything after `--` is handed to clickable (`-- --verbose`).

Then tap the icon, or

    ssh phablet@<device> lomiri-app-launch photoncamera.thekit_photoncamera_0.97.1

`lomiri-app-launch`'s exit code is not the answer: it prints `Started: <id>`,
hands off and then dies on its own registry teardown. Read what it said.

`PC_MALIIT_DIR` overrides the maliit-glib directory `stage-prebuilt.sh` copies
from; `stage-prebuilt.sh --force` restages when the sha check would otherwise
skip.

The version is the app's `versionName` from `app/build.gradle` plus a packaging
revision — `0.97.1` today. Bump `CLICK_REV` in `build.sh` when the packaging
changes but the app does not: OpenStore refuses an upload whose version it has
already seen.

## CI

`.github/workflows/kn-click.yml` runs the self-contained build on every push to
`kn` that touches `kn/**`, `ui-compose/**`, the assets or `clickable.yaml`, and
on `workflow_dispatch`. An ordinary x86_64 runner: this is the amd64 cross
container, and `kn/` is a standalone Gradle build with no Android modules, so
the workflow deletes the runner's Android SDK rather than configuring it.

Two things are cached, and both are keyed by the file that decides their
contents rather than by a date:

* `kn/deps/{aurora-maven,sysroot-arm64}`, keyed by `scripts/fetch-deps.sh` —
  922 MB over git-lfs from hub.mos.ru and 141 MB of debs from ports.ubuntu.com,
  the slowest and least reliable part of a run. `kn/deps/atl-touch` is
  deliberately *not* cached: it is a moving master and `kn/gen-atlas` is
  generated from whatever it is that day.
* `kn/out/click/.clickable/home`, keyed by `build.gradle.kts`,
  `gradle.properties` and the wrapper properties. clickable points `HOME` at
  `${BUILD_DIR}/.clickable/home`, so the container's `~/.konan` and `~/.gradle`
  land inside the workspace; konan's bundle and its LLVM are most of that.

A `checks` job parses every script, the YAML and the substituted manifest, and
checks the hook against the `.desktop` basename, before the hour-long build
starts — the packaging mistakes that are otherwise found at the end of it.

`clickable review` runs but **cannot fail the build**: `picture_files` is a
standing NEEDS REVIEW finding (below), so a blocking review would mean a
permanently red workflow. Its output is in the run summary, and reading it after
a packaging change is the point.

A push to `kn` publishes the click as a GitHub prerelease tagged
`kn-v<version>-<sha>`, because an Actions artifact needs a login to download and
a tester does not have one. Nothing is uploaded to the OpenStore: the last
section of this file is what a human has to settle first.

## What is unresolved

**`clickable build --arch arm64` has now been run both ways and both produce a
click** (podman, 2026-09-18, this box):

* **from source in the container** — `fetch-deps.sh`, the drawables, mgwl, the
  extra arm64 libraries, the natives, atlas's camera backend and the Gradle link,
  all inside clickable's amd64 cross container, with `-PwithApp`: `BUILD
  SUCCESSFUL`, a 57 MB click, and `readelf -d` on the packaged binary showing the
  expected `DT_NEEDED` set with `libmaliit-glib.so.0` as the only bundled
  library. Gradle came from the repository's own `gradlew` (8.11.1, not the
  host's 8.13) and that was fine.
* **from the staged tree** — the same command with
  `CLICKABLE_ENV_PC_CLICK_BUILD=staged`, in seconds.
* `bash -n` on every script, the YAML parses, the manifest is valid JSON,
  `stage-prebuilt.sh` is idempotent, and `build.sh` fails usefully on a wrong
  `ARCH`, a missing prebuilt, and a library that is neither on the device nor
  available (tested by deleting `libzstd.so.1` from `device-libs.txt`).
* `clickable review --arch arm64`: **one** finding, below. The 128×128 icon and
  the `.desktop` `Categories` were *not* flagged.

**Nothing here has been run on a phone.** Everything below is reasoned, not
observed.

1. **Confinement versus libhybris.** The confined `camera` group is what a
   Qt/QML camera app uses, and that one reaches the camera through media-hub.
   This app reaches it through `android_dlopen` directly: `/dev/binder`,
   `/dev/ion` or `/dev/dma_heap`, and reads under `/vendor/lib64`. Whether the
   24.04 `camera` group covers that is **unverified**. If it does not, the
   symptom is `android_dlopen(libcamera2ndk.so) failed` in the log, and the two
   ways out are `read_path`/`write_path` entries in the apparmor JSON for
   exactly what is denied (check `journalctl -k | grep DENIED`), or
   `"template": "unconfined"` — which is what `linux-port/click` settled for and
   which **blocks OpenStore submission** (`security:template_valid` is a NEEDS
   REVIEW finding, not a local-install one).
2. **One variable is the root of two different things.**
   `Context.defaultHome()` and `Environment.root()` both read
   `PHOTONCAMERA_HOME`, so `shared_prefs/`, `files/` and `cache/` cannot be
   separated from `DCIM/`. Putting the lot under `~/Pictures/PhotonCamera` is
   what makes a capture visible to the gallery with one policy group, at the
   cost of three housekeeping directories sitting in a user-visible folder. The
   clean fix is one line in `AndroidContentContext.defaultHome()`: a second
   variable for the data root, pointed at `~/.local/share/<pkg>`. Not taken here
   because this directory may not touch the app's sources.
3. **`appdir_get_path` for anything other than package files.**
   `host/appdir_stub.c` answers `APP_DATA` and `APP_CACHE` with
   `$ATL_APPDIR/{data,cache}` — inside the read-only package. Nothing asks
   today (CMP uses `PACKAGE_FILES` only), but a klib that starts to will get an
   unwritable path with no useful error.
4. **The image codec differs between the two build paths, and that is a
   property of the machine.** `host/natives/build.sh` probes for `jpeglib.h`
   and `png.h`: the clickable container has both, so the container build links
   the system libjpeg and libpng and the binary gains `libjpeg.so.8` and
   `libpng16.so.16` — both on the device, so nothing extra ships. A box without
   those headers (this one) gets the vendored stb instead, at lower JPEG
   quality. `kn/scripts/fetch-deps.sh` puts libjpeg and a `libpng.so` alias in
   the sysroot so that *either* answer links; without them the link dies with
   `ld.lld: unable to find library -ljpeg` after twenty minutes of compiling.
5. **`clickable review` fails on one reserved policy group.**
   `security:policy_groups_safe:photoncamera:picture_files` — "(NEEDS REVIEW)
   reserved policy group 'picture_files': vetted applications only". It is a
   local-install non-issue and an OpenStore one: the submission has to be vetted
   for that group, or the app has to write somewhere `picture_files` does not
   cover, which would take the captures out of the gallery.

## What a human must do before the first OpenStore submission

* **An icon.** `fastlane/.../icon.png` is 128x128 and is what the build stages.
  OpenStore wants a square PNG of at least 256x256; PhotonCamera's real launcher
  icon is an adaptive one — three Android vector drawables — so somebody has to
  rasterise it once at a decent size and put the result here.
* **Screenshots**, at device resolution. `scripts/run-phone.sh`'s `PC_SHOT` path
  produces them straight off the GPU; there is no screenshot tool on Ubuntu
  Touch and Lomiri exposes no D-Bus method for one.
* **Licence.** The repository is GPL-3.0 (`LICENSE`); the OpenStore listing has
  to name it, and the bundled `libmaliit-glib` is LGPL-2.1 and has to be
  declared as a bundled third-party library.
* **Decide the confinement question** (item 1 above) on a real device. An
  unconfined click cannot be published.
* **Source URL and description** for the listing, and a maintainer address that
  is meant to receive mail — `manifest.json` currently carries
  `TheKit <nekit1000@gmail.com>`.
* **Deal with the `picture_files` finding.** `clickable review --arch arm64`
  fails on it today (item 5 above): it is a reserved group, so the submission
  needs vetting. Re-run the review after any packaging change and read every
  finding before uploading.
